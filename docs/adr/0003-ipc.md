# 0003: IPC boundaries and the `neuectl` protocol

- **Status:** Accepted
- **Date:** 2026-11-03

## Context
neueOS has three kinds of inter-process talk: the compositor with its own shell, the
compositor with tools (`neuectl`, tests, coding agents), and services with everyone. PLAN.md
§3 names Wayland, "Unix socket + JSON" and D-Bus without saying which goes where. The
compositor is single-threaded on calloop and must never block (ADR 0001).

## Decision
### Which channel for what
| Between | Channel | Why |
|---|---|---|
| Compositor ↔ shell (dock hints, minimise targets, window list, app state, menu addresses, injected shortcuts) | **Wayland**: the private `neue-shell-v1` protocol, designed in Phase 3 | Tied to surfaces and objects; no extra socket; access control via `security-context-v1` |
| Compositor ↔ tools, tests, agents | **`neuectl` socket**: JSON over a Unix socket (below) | Scriptable from any language; no Wayland client needed |
| Services ↔ shell, apps, Preferences | **D-Bus** (session or system bus) via `zbus`, names under `org.neueos.*` | Standard for desktop services, activation, polkit |
| Third-party apps ↔ desktop | Wayland protocols and xdg-desktop-portal | Standard |

The compositor does **not** link zbus in Phase 1. Things that look like they need D-Bus
in the compositor go elsewhere: global-menu D-Bus work lives in the shell (ADR 0005),
screen capture for the portal uses `ext-image-copy-capture`, and logind access goes
through libseat. If a later feature really needs D-Bus in the compositor, it needs a new
ADR (it would mean a zbus executor bridged into calloop).

### The `neuectl` protocol
- **Crate:** `neue-ipc` (portable) holds the serde request, reply and event types and a
  small blocking client. `neue-comp` serves it; `neuectl` (in `compositor/`) is the CLI.
- **Socket:** `$XDG_RUNTIME_DIR/neueos/comp.$WAYLAND_DISPLAY.sock`, mode 0600 in a 0700
  directory. The compositor exports its path as `NEUE_SOCKET` to children; clients use
  `NEUE_SOCKET` if set, else derive it from `WAYLAND_DISPLAY`. Flatpak sandboxes don't see
  this directory, which is intended.
- **Framing:** newline-delimited JSON, UTF-8, one object per line, at most 1 MiB per line.
- **Requests:** `{"id": 1, "request": "windows"}` or
  `{"id": 2, "request": "action", "params": {"name": "close-window", "window": 42}}`.
  `id` is chosen by the client and echoed back.
- **Replies:** exactly one per request, in order:
  `{"id": 1, "ok": <payload>}` or
  `{"id": 2, "error": {"code": "unknown_window", "message": "…"}}`. Error codes are
  `snake_case` strings, stable once shipped.
- **Events:** `{"id": 3, "request": "subscribe", "params": {"topics": ["windows", "spaces"]}}`
  is answered with `ok`, then the connection carries only event lines
  (`{"event": "window_opened", "data": {…}}`) until the client disconnects. A subscriber that
  falls more than 1 MiB behind is disconnected; it can reconnect and re-query.
- **Versioning:** `{"request": "version"}` returns the compositor version and a protocol
  integer. Changes are additive (new requests, fields, events, codes); clients ignore
  unknown fields. Breaking changes bump the integer.
- **Initial requests (Phase 1):** `version`, `windows`, `outputs`, `spaces` (single Space
  until Phase 4), `focused-window`, `action` (named, see `neuectl actions`), `actions`,
  `reload-config`, `screenshot` (writes a PNG to a client-given absolute path; encoding runs
  off the event loop; details in ADR 0024), `subscribe`, `quit`.
- **Event loop:** the listener and every connection are non-blocking calloop sources with
  per-connection read and write buffers. No request may block; slow work (PNG encoding,
  file writes) runs on a worker thread and replies through a calloop channel.
- **Trust:** anyone who can open the socket is the user and may do anything the user can.
  There's no authentication beyond file permissions.

## Consequences
- `neue-ipc` types are the contract for tests and agents; keep them documented and
  changes additive.
- The shell gets no special powers through the socket; everything it needs goes into
  `neue-shell-v1`, which gets its own ADR in Phase 3.
- `cargo xtask` and VM tests drive the session through `neuectl` only.

## Alternatives considered
- **D-Bus for `neuectl`:** needs a bus in the compositor and is awkward from shell scripts.
- **JSON-RPC 2.0:** heavier envelope (batches, notifications) with no benefit for one
  client per connection; our envelope maps onto it if ever needed.
- **One request per connection (niri style):** simpler, but tests issuing many queries pay a
  connect each time; ours allows both.
- **Shell talking to the compositor over the socket:** duplicates object identity that
  Wayland already gives us, and gives up `security-context-v1` filtering.
